# Mikoshi 总体方案 · 易读版

**待审提案 v0.2｜2026-10-18｜按用户反馈重设计，尚不启动裁剪或开发。**

这一版按你的业务划分来组织：**先进入可自行定制的数据大看板，再进入三方号、KOL、联动管理、创意管理、VPC虚拟社区、整体业务中台六个板块。** 每个板块都有自己的完整工作流程，任务、资料、审批、费用和AI能力在里面直接使用。

你不需要先把所有工作盘清楚。现有材料已经足够支持第一版整体结构；具体业务规则和预算在对应阶段继续核实。完整依据、后端设计和异常处理见 [详细方案](DESIGN_PROPOSAL.md)，阅读范围见 [调查索引](../../../Product/research/2026-10-18-mikoshi/SOURCE_INDEX.md)。

## 登录后的第一屏：你自己的数据大看板

每个人都能自己选择卡片、拖拽布局、调整大小、切换图表、设置项目和时间范围。可以保存“我的日常”“某个传播节点”“月度复盘”等多个看板，并设一个默认首页。

首次使用有岗位模板，不用从空白搭起。负责人可以看总体节点和费用；三方号同学可以看待审、发布和账号表现；KOL同学可以看锁档与交付；研究人员可以看VPC社区与实验。也可以混合几个板块的数据。

个人版跨设备保存；团队版由有权限的人共同维护，大家也可复制成自己的版本。**共享看板布局不会扩大数据权限**。每张卡标明来源、更新时间、缺数情况，真实效果、计划目标和虚拟社区模拟数据分开显示。

“编辑看板”主要是改布局、组件、筛选和展示。要改费用、稿件或账号事实，进入有权限的业务记录办理。首页刷新只读已有数据，不会自动花token或重新开爬。

## 六个业务板块

| 板块 | 在里面完成什么 |
|---|---|
| **三方号** | 账号、供应商与运营人 → 定位/月度计划 → 内容审核 → 发布 → 效果、整改。先在其中区分供应商与伏羲业务线。 |
| **KOL** | 达人资源 → 选人/比选/报价 → 锁档与合作单 → 创意、内容交付 → 发布效果与合作复盘。 |
| **联动管理** | IP/机构/品牌合作 → 权益与限制 → 产品/传播交付 → 素材监修 → 履约、费用与续期。 |
| **创意管理** | 需求Brief与洞察 → 点子/提案 → 评审与验证 → 制作Brief → 交给业务执行 → 案例复盘。 |
| **VPC虚拟社区** | 虚拟玩家与圈层 → 话题/活动/访谈 → 受控模拟与实验 → 反馈报告；长期社区演化逐步验证。 |
| **整体业务中台** | 总项目/传播节点 → 跨板块工作包与依赖 → 资源、预算和风险协调 → 汇总真实交付与复盘。 |

三方号管持续运营，KOL管一次合作的约定交付；联动管权利和履约，创意管方案与表达。各板块里都能直接看本业务的资料、任务、审核、费用与AI，底层共用同一套能力。

首页和整体业务中台也有区别：**首页展示“我关心什么”，中台办理“几条业务怎样协同完成一件事”。** 中台能协调目标和资源，但不另存一套三方号数据、达人合同或创意稿。

## 几个板块怎样一起工作

例如做一次联动传播：

1. 中台确定目标、节点、参与业务与预算。
2. 联动管理给出可用权益、素材和监修要求。
3. 创意管理形成方案和制作Brief；需要时委托VPC做模拟反馈。
4. KOL落实达人合作，三方号安排账号内容；分别完成审核、发布与回执。
5. 效果和费用回到中台复盘，经验进入创意案例与知识库。

普通账号日常稿可以在三方号内部完成；不是每件小事都必须走遍六个板块。同一素材被多业务使用时引用同一版本，同一成本分摊后不能重复计入总盘。

## 首先做一条真的能用的业务链

首期仍建议选**一个传播节点**，用一份母素材、必要的监修、一个合作交付和少量账号验证；具体先做哪条业务仍待你确定：

**目标 → 授权素材 → 合作与任务 → AI起草/人审 → 排期发布 → 回执与效果 → 费用归属 → 复盘沉淀。**

第一版同时提供可定制首页的基础组件和个人保存能力。已接通什么业务就展示什么，未接入的卡片明确提示；六个业务的完整菜单可以分期展开。

先允许人工发布并回填证据，再逐步接可靠自动化。草稿写完不等于发布成功，发布完成也不等于已经结算。

## VPC玩家和工作AI，各有自己的位置

VPC沿用你这次的名字，现有VCPAI是它的技术资产候选。它可以有虚拟玩家、圈层、话题与活动，也可以为创意和联动做研究；画像、群聊模拟与实验已有积累，跨日关系和持续社区演化仍需新建、验证。

**虚拟玩家在社区里参与模拟；工作AI替团队处理业务。** 玩家不会因为会聊天就拿到公司资料或发布权限。研究主持AI在获准范围内运行社区/实验，报告始终标明模拟身份，不能冒充真实市场结果。

## 工作AI怎样长期工作

每个居民有稳定名字、岗位、主管、技能、权限、记忆和工作履历。换模型不需要换居民。它们平时等待事件，有工作才被唤醒，因此不必全天烧token来维持常驻。

第一批建议只开2–3种岗位，例如项目值班员、内容助理、知识管家。每个业务里能看到自己的AI同事；中台统一管名册、配额和异常接管。以后可以增加合作助理、创意研究主持人和渠道巡检员。可以有20位居民，但同时只让几个工作；人数与费用、运行槽位分开管理。

DeepSeek等成本优先模型先承担短而明确的任务：整理、抽取、分类、起草。金额、权限、日期、状态和引用由程序校验；资料不足就报告不足，做不好就有限重试或交给人工/获准的更强模型。具体型号通过任务评测选择。

居民可以有风格，但不能自己扩大权限、预算或给自己批准新技能。整理建议可自动产生；对外发布、正式口径、费用承诺等按明确授权执行。AI小镇可以是有趣的状态视图，真正的运行底座不依赖动画。

## 旧项目各自放哪里

| 原资产 | 建议成为的部件 | 当前需要补的主要能力 |
|---|---|---|
| OpenBP | 工作台、资料与任务协作 | 多人隔离、统一业务对象、去掉多份状态来源 |
| Torpedo | 知识库、证据、研究与知识管家 | 生产接线、恢复与权限；长期Agent设计已有重要基础 |
| Crawler F1 | 采集执行节点 | 中央排队、身份映射、快照入库和节点运维 |
| Harness | 受控工具/代码执行候选 | 当前桌面阶段边界及服务器适配 |
| Kiroshi | 授权观察与感知候选 | 现阶段主要是设计和探针，需继续验证 |
| VCPAI | VPC虚拟社区的画像、互动与实验基础 | 修复授权缺口；长期社区演化另验，模拟结论保留身份 |
| Business Map | 业务环节、规则、交接和演练参考 | 芯片式执行内核尚未实现，先把能力合同定义好 |

其中CF1目前是Windows本机产品，有可见浏览器、登录确认与既定任务合同，且当前Mission仍串行。建议中央平台上服务器，CF1先留在专用Windows节点。新采集任务仍遵守原确认流程；不能直接宣称全自动、多平台并行、40人随便同时开爬。

## 后端怎样撑住

建议一个模块化业务核心，延续OpenBP工作台；PostgreSQL保存业务事实与权限，私有对象存储保存文件，专业Worker执行研究/模型/采集。长期任务优先验证Temporal这类持久编排，避免重启就忘记做到哪里；生产部署方式和运维成本要先验证。

每人有自己的登录与权限，每个AI也有独立身份。能看什么、能执行什么、能花多少钱，都由后端决定。40个人不意味着40个模型或浏览器同时运行，后台需要排队、公平分配和预算限制。

系统必须认真处理一种情况：**请求发出去了，但不知道是否成功。** 此时先查证，不能自动再发布一次、再采一次。服务器重启、恢复备份时同样要先对账。

首期规模足以采用较简单的服务结构，但要有备份、监控和恢复演练。服务器规格、响应速度与恢复时间在详细版里是待测目标，没有冒充现有能力。

## 推进顺序

1. 你审这份总体提案，决定方向和首个业务闭环。
2. 我做精细裁剪清单，逐项写保留/改造/归档/移动、理由和恢复方法，再按授权执行。
3. Claude按具体SPEC完成公共底座、自定义首页基础能力和第一条业务链，我独立验收。
4. 接CF1快照与Torpedo知识链，再启用第一批AI居民。
5. 按业务优先级扩展六板块、团队看板与VPC社区试点，达到约40人长期使用所需的权限、负载与恢复验收。

不会一次把所有旧项目硬合并。原有Constitution与SBS规则继续有效；通过这份提案也不自动批准每一个删除项或对外动作。
