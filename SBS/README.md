# Step By Step 开发流程

每次动手前先有计划，再有明确验收标准；完成后用证据验收。**当前步骤通过后，才能创建下一份编号SBS。** 未验收时的未来想法留在 [研究问题池](../Product/RESEARCH_BACKLOG.md)，不提前创建下一份SBS来绕过顺序。

## 状态

| 状态 | 含义 | 下一动作 |
|---|---|---|
| DRAFT | 当前步骤正在补齐目标、范围和标准 | 研究并完成准入条件 |
| READY | 授权、基线、范围、依赖和验收已足够明确 | 开始本步实施 |
| IN_PROGRESS | 正在执行本步计划 | 实现并保留实际记录 |
| VERIFYING | 实现者已提交，正在独立验收 | 通过或退回本步修复 |
| BLOCKED | 本步存在无法独立解除的具体阻塞 | 记录解除条件，继续本步不依赖阻塞的工作 |
| ACCEPTED | 所有必需验收项均有有效证据并通过 | 归档后方可创建下一份编号SBS |
| CANCELLED | 用户明确取消或替换当前步骤 | 记录未完成范围、原因与后续授权，不伪称验收通过 |

正常流转：DRAFT → READY → IN_PROGRESS → VERIFYING → ACCEPTED。返工：VERIFYING → IN_PROGRESS → VERIFYING。BLOCKED解除后回到记录的原状态。

同一时刻只有一份未完成的顶层编号SBS，包括DRAFT。一个步骤内允许彼此独立的并行子任务，必须指定文件/仓库归属和统一验收；这不允许启动另一个顶层步骤。各子项目原有SBS是历史独立流程，顶层不批量改变它们；进入组件实施时在本步中引用和协调其有效门禁。

用户若明确取消或替换当前步骤，记录该决定、未完成项和影响后标记CANCELLED；这是用户改变范围的例外，不是执行者跳过失败验收的方法。

## READY 准入

必须已写清：目标与非目标、有效授权、目标仓库/分支/基线、已有改动、实施步骤、受影响合同与数据、验收标准和证据方法、风险/回滚、阻断问题。适用项缺失时不能 READY；不适用项写明理由，不堆空字段。

范围内可逆的实现细节由执行者解决。没有产品意义的未知项不必让用户选；会改变产品语义、跨组件合同或权限的未知项必须先解决。

## 实施与变更

先保存SBS，再修改被管理的文件。本次首次建档用SBS-0001先落计划；这是启动顺序，不是永久豁免。

扩围前更新范围、风险和验收映射，保留前版本与原因。不能为了让已有实现通过而降低标准。规格改变后，标记受影响证据过期，按需要重验。

## 验收门禁

每条AC必须有明确结论：PASS、FAIL、NOT_RUN或NOT_APPLICABLE。NOT_APPLICABLE需在计划或有依据的变更中说明；FAIL/NOT_RUN不能算通过。mock、静态、集成和真实外部验证分别标注。

实现者自测只触发VERIFYING。未参与实现的独立审查者核对实际证据，列明返工项；所有必需AC通过后才可ACCEPTED。用户已授权的客观技术验收可完成后自主记录，不伪称用户人工确认。

ACCEPTED后出现的新缺陷通过后续SBS修复，并链接原验收；保留历史事实。若发现原验收证据无效，先撤销该结论的有效性并记录影响，不继续依赖它实施。

## 结束记录

更新SBS正文、验收记录和INDEX；写明实际交付、差异、命令与环境、证据路径、未覆盖边界、提交版本和下一研究入口。发布、部署、本地提交和远端同步分别报告。不得把本步PASS扩展为整个产品已完成。
